# service-monitor —— 跑长任务时，让手机替你盯着

```
你的任务（训练 / 备份 / 构建 / 部署 / 等一个 API 结果）
        │
        │  每 30 秒看一眼：好了没？
        ▼
   监控脚本  ──好了──▶  手机通知（响一声）
        │
        └─ 自己退出，不留后台进程
```

一个跑 6 小时的任务，你不需要每 20 分钟去看一眼进度条。让脚本盯着，跑完了推一条消息到手机。

**它不依赖你的电脑开着**。监控跑在**任务所在的那台机器**上，你合上笔记本、出门吃饭、手机在兜里，都不影响。

---

## 一、它解决的具体问题

「跑完告诉我」这句话，实际做起来有一堆坑：

| 你可能这么干过 | 问题 |
|---|---|
| `nohup python train.py &` 然后时不时 `tail -f` | 得盯着，离开电脑就不知道进度 |
| 写个 `while` 循环等文件 | 忘了设心跳，脚本偷偷死了你不知道 |
| 用「日志文件出现了」当完成信号 | 日志是**边跑边写**的，你拿半成品数据算出了错结论 |
| 用 `curl` 往推送服务发消息 | 没加 `-f`，服务器返回 400 你也以为发出去了 |
| 盯了 6 小时，结果手机静音没响 | 白等 |

这个 skill 就是把这些坑一次性填掉。它做三件事：

1. **提供一个不会说谎的循环**（心跳、超时、异常终止检测、退出码校验、日志轮转，全都内置了）
2. **提供一个唯一的推送出口**（优先级映射、重试、审计日志，不让每个脚本自己拼 `curl`）
3. **提供一套规矩**（哪些信号不可靠、推送里不能放什么、测试消息怎么发）

你只需要回答三个问题：**叫什么名、怎么算好了、好了之后推什么。**

## 二、5 分钟上手

### 第 1 步：初始化（只做一次）

```bash
ctl init
```

它会创建 `~/.notify/`，装上发送器、循环库和配置文件，并**生成一个随机频道名**，格式是 `<你的用户名>-main-<16 位随机串>`，像这样：

```
主频道已创建：me-main-pn9jmrgvpuvjmmww
手机装 ntfy（App Store / F-Droid 都有），订阅这个名字即可。
```

前缀（`me`）取自你的系统用户名，只是为了在手机通知里一眼认出是哪套系统；想改就设环境变量 `TOPIC_PREFIX`。

> **频道名 = 密码。** ntfy 是开放的，任何知道频道名的人都能读到你的消息，也能往里发假消息。名字里的 16 位随机串就是用来防这个的。**不要把它放进博客、GitHub 仓库或截图里。**

### 第 2 步：在手机上订阅

装 [ntfy](https://ntfy.sh/#subscribe)，添加订阅，输入上一步的频道名。

### 第 3 步：验证链路

```bash
ctl test <你的服务名>
```

手机上应该响一声，标题是 `[你的服务名] 【测试】通道自检`。

**这一步没通过就不要往下走。** 频道名打错是最常见的失败原因，而且服务端完全看不出来——`curl` 照样返回 200，你以为发出去了。

## 三、给一个任务配监控

### 3.1 复制模板

```bash
mkdir -p <你的项目>/.monitor
cp templates/monitor.sh <你的项目>/.monitor/train.sh
```

### 3.2 只改三个变量

```bash
SVC='train'                                  # ① 叫什么（小写连字符）
CHECK='test -f out/final_model.pt'           # ② 退出码 0 = 真的好了
BODY='du -h out/final_model.pt | cut -f1'    # ③ stdout 最后一行 = 通知正文
```

然后按需加两三个参数（不加也能跑）：

```bash
STABLE=60            # 判断通过后再等 60 秒复检，防止"文件写到一半"被当成完成
TIMEOUT=43200        # 最长等 12 小时，超时推一条 warn 然后退出
WATCH_PATTERN='train.py'   # 进程没了但条件没满足 → 立刻告警「异常终止」
```

### 3.3 验证判断逻辑（很重要）

```bash
# 条件还没满足时，CHECK 必须返回非 0
bash -c 'test -f out/final_model.pt'; echo $?     # 应该是 1，不是 0
```

如果这里返回 0，说明你的 CHECK 写成了**恒真**，监控会立刻"完成"并推送——这是最常见的错误。

### 3.4 后台启动

```bash
tmux new-session -d -s train \
  'bash <你的项目>/.monitor/train.sh >> ~/.notify/logs/train.log 2>&1'
```

**必须套 tmux。** SSH 一断，前台进程会被 SIGHUP 杀掉；tmux 让脚本的父进程变成 tmux，断线不影响。

> 不要写成 `... | tee ~/.notify/logs/train.log`——管道会吞掉退出码。

### 3.5 收工

任务跑完后脚本自己发通知、自己退出、自己清锁。你不需要做任何事。

## 四、一个监控到底是怎么运行的

这部分解释「它在哪、占多少资源、什么时候消失」。

### 它在哪

```
<你的项目>/.monitor/train.sh          ← 监控脚本本体（你写的）
~/.notify/lib.sh                      ← 循环引擎（不用改）
~/.notify/notify                      ← 唯一推送出口（不用改）
~/.notify/config                      ← 频道、优先级配置
~/.notify/services/train.conf         ← 该任务的独立频道（只在用了 new-channel 时存在）
~/.notify/logs/train.log              ← 运行日志
~/.notify/state/train.lock/pid        ← 进程锁（运行期间存在）
~/.notify/sent.jsonl                  ← 所有推送的审计记录
```

### 占多少资源（实测）

| 项目 | 实测值 | 说明 |
|---|---|---|
| 内存 | **2.8 MB** | 一个空 bash 进程的成本 |
| CPU | **0.0 %** | 99.9% 的时间在 `sleep 30`，醒来只跑一条 `ls`/`grep` |
| 磁盘 | 约 8 KB/小时 | 每 30 秒一行检查日志，一天约 200 KB（超过 5 MB 自动轮转） |
| 子进程 | 每次检查临时创建一个 sleep | 检查完立即消失 |

十个监控加起来不到 30 MB 内存。它不影响你的训练任务。

### 什么时候消失

四条退出路径，**全部是脚本自己走完就退**，不需要你清理：

```
循环 ──┬─ ① 条件满足 ────────→ 取摘要 → 推送「完成了」→ return 0 → 退出
       ├─ ② 超过 TIMEOUT ────→ 推送「超时未完成」──→ return 1 → 退出
       ├─ ③ 进程没了但没完成 ─→ 推送「异常终止」───→ return 5 → 退出
       └─ ④ 被 kill / Ctrl-C ─→ trap 捕获 ─────→ 清锁 → 退出
```

关键的一行是：

```bash
trap "rm -rf '$LOCK'" EXIT INT TERM
```

意思是「**不管你怎么结束，结束前先把锁清掉**」。`EXIT` 管正常结束，`INT` 管 Ctrl-C，`TERM` 管 kill。所以永远不会有残留锁卡住下一次启动。

脚本退出后，tmux 会话因为没有前台进程跟着销毁。**留下的只有日志文件**（故意保留，供事后查）。

### 它不会碰你的任务进程

监控只做两件事：`ls` 看文件在不在、`ps` 看进程还在不在。**从不 kill 任何东西**。任务怎么结束是任务自己的事。

## 五、通知级别与优先级

只有**四个语义级别**，不接受数字：

| 级别 | 什么时候用 | 推送到手机的表现 |
|---|---|---|
| `done` | 任务完成 | 响一声 + 弹窗 |
| `warn` | 超时 / 异常终止 | 响一声 + 弹窗 |
| `start` | 任务启动 | 静音，不打扰 |
| `info` | 进展播报 | 静音 |

想改档位不动代码，改 `~/.notify/config`：

```bash
PRIORITY_DONE="${PRIORITY_DONE:-high}"     # 可选 min / low / default / high
PRIORITY_INFO="${PRIORITY_INFO:-low}"
```

### 为什么不存在 priority 5

ntfy 支持 1~5 五档，其中 **5（max）在安卓上是「闹钟式通道」——会一直响到你手动划掉通知为止**。

这个 skill 从设计上就不允许出现 5：

- `notify` 命令行只接受 `done/start/warn/info` 四个词，传数字直接报错
- `PRIORITY_DONE` / `PRIORITY_INFO` 只校验 `min|low|default|high`
- 监控模板里没有一行 `curl`，绕不过去

这是为了根治一个具体事故：有人用 5 发了一条「澄清消息」，结果手机在会议室里响了整整两分钟。

### 不同手机不一样

同一个 `high`，在有的手机上会弹横幅，在有的手机上被系统静音了。如果你的手机对 `high` 没反应，先跑：

```bash
notify done "【测试】high 档位" "如果这条不响，把 PRIORITY_DONE 改成 default 试试"
```

然后按结果调整 `~/.notify/config`。

## 六、四个现成的用法

任何能写成「一条返回 0 / 非 0 的命令」的条件都能接入。这四个只是起点：

| 类型 | 典型场景 | `CHECK` | `BODY` |
|---|---|---|---|
| **完成型** | 训练 / 备份 / 构建 | `test -f out/done.json`（配 `STABLE=60`） | `du -h backup.sql.gz \| cut -f1` |
| **响应型** | 等一个 Agent 的回答 / 等 API 终态 | `grep -q '"status": *"completed"' resp.json` | `tail -1 answer.txt` |
| **内容型** | 网页或日志出现关键字 | `curl -sf https://x/status \| grep -q "已上线"` | `grep -o "版本 v[0-9.]*" deploy.log \| tail -1` |
| **阈值型** | 进度到达 100% | `[ "$(cat progress.txt)" -ge 100 ]` | `cat progress.txt` |

### 例：等一个 Agent 的回答

```bash
SVC='agent-codex'
CHECK='test -s /tmp/agent_codex_answer.txt'
BODY='tail -1 /tmp/agent_codex_answer.txt'
WATCH_PATTERN='codex'      # Agent 进程挂了立刻告警，别傻等
TIMEOUT=3600
```

## 七、收不到通知？三步定位

推送是个**单向**过程——服务器无法知道手机有没有响。所以排查要靠分界线：**问题在发送端还是接收端？**

```bash
# ① 确认真的发出去了，且优先级正确
tail -3 ~/.notify/sent.jsonl
#    看 "http":200 和 "priority"

# ② 发一条测试，看是通道问题还是单条问题
ctl test <服务名>

# ③ 判断
#    test 也不响        → 手机侧问题（通知权限、渠道静音、后台被杀）
#    test 响、生产不响  → 脚本侧问题（看 sent.jsonl 有没有记录）
```

`sent.jsonl` 是关键证据：**有记录 = 发出去了，没记录 = 脚本根本没走到推送那一步。**

### 手机侧常见原因

| 现象 | 原因 | 处理 |
|---|---|---|
| 完全收不到 | 频道名打错 / 没订阅上 | 重跑 `ctl test`，对照频道名 |
| 后台清了就收不到 | ntfy 靠长连接，进程被杀就断 | 见下方「已知限制」 |
| 有通知但没声音 | 该优先级对应的通知渠道被静音 | 系统设置里找 ntfy 的通知渠道，单独开声音 |
| 响个不停停不下来 | 用了 priority 5 | 本工具不会发 5；若手动 `curl` 发过，改用 `notify` |

## 八、已知限制（务必先看这一节）

### 1. ntfy 需要 App 活着

微信能"杀后台也收得到"，是因为它走**厂商推送通道**（华为 PUSH / 小米推送 / OPPO、vivo 推送）——消息由**系统级常驻进程**代收，能唤醒已死的 App。

ntfy 官方也支持等价的 **FCM**（Firebase Cloud Messaging），但国内需要 Google Play 服务 + 能连 `mtalk.google.com`，**基本不可用**。

所以 ntfy 在国内只能退回"自己维持长连接"，**App 进程被杀 = 收不到**。

能做到的缓解：

```
① ntfy App 里开启「保持后台连接」+ 允许常驻通知（前台服务）
② 系统「应用启动管理」里把 ntfy 改成手动管理，自启动/关联启动/后台活动全开
③ 电池优化白名单：不优化
④ 多任务界面里给 ntfy 加锁，防一键清理
```

调完能扛住"清理后台"，但**手机重启后必须手动开一次 App**。

### 2. 想要"系统级必达"，需要换后端

如果你的通知不能漏（比如等一个跑一整夜的结果），可以考虑走微信通道的方案：

| 方案 | 通道 | 可靠性 |
|---|---|---|
| Server酱 / PushPlus | 微信公众号模板消息 | ⭐⭐⭐⭐⭐ |
| 企业微信 / 钉钉机器人 | 对应 App | ⭐⭐⭐⭐⭐ |
| Bark | Apple APNs（仅 iOS） | ⭐⭐⭐⭐⭐ |

**好消息是这个 skill 的架构支持换后端**：推送的唯一出口是 `~/.notify/notify`，业务脚本只调它。换后端 = 改 `notify` 这一个文件，`monitor_loop`、模板、日志全都不动。

### 3. 服务器重启会丢监控

tmux 不持久化。机器重启后需要重新启动监控脚本。长任务建议把启动命令写进一个 `run.sh`，重启后一行拉起来。

### 4. ntfy 公共服务器不加密存储

ntfy.sh 免费版的消息在服务端**明文存储**，默认保留一段时间。所以：

- 正文里不要放密钥、token、内部地址、真实用户数据
- 敏感项目自己搭 ntfy 服务端，把 `NTFY_SERVER` 指过去

## 九、常用参数速查

写在监控脚本的「按需调整」区，不写就用默认值：

| 变量 | 默认 | 作用 |
|---|---|---|
| `INTERVAL` | 30 | 多久检查一次（秒） |
| `STABLE` | 0 | 判断通过后等几秒复检，防"写到一半" |
| `HEARTBEAT` | 1800 | 每 30 分钟打一行「还在等」。**别关**，它是脚本的呼吸 |
| `TIMEOUT` | 0（无限） | 最长等多久，长任务建议设成预期的 1.5 倍 |
| `WATCH_PID` | 空 | 目标进程 PID，消失而条件未满足 → 告警「异常终止」 |
| `WATCH_PATTERN` | 空 | 用命令行特征代替 PID |
| `BODY_MAX` | 300 | 推送正文字符上限（按字符截，不会切坏中文） |
| `TITLE_DONE` | 「完成了」 | 自定义完成通知的标题 |

### 为什么 HEARTBEAT 不能关

没有心跳日志时，「**任务还在跑**」和「**监控脚本已经死了**」在日志里看起来完全一样——都是没有新输出。

有了心跳，日志每 30 分钟多一行 `💓 还在等，已等 N 分钟`。哪天这行不出现了，你立刻知道是监控出问题，而不是任务特别慢。

## 十、目录结构

```
service-monitor/
├── SKILL.md                 给 agent 看的操作说明（含 13 条判断规矩）
├── README.md                本文件，给人看的完整手册
├── scripts/
│   ├── notify               唯一推送出口：级别→优先级映射、重试、审计
│   ├── lib.sh               循环引擎：锁、心跳、超时、异常检测、日志轮转
│   └── ctl                  安装与管理：init / new-channel / test / status / stop
└── templates/
    └── monitor.sh           监控脚本模板，复制后只改 3 个变量
```

### `ctl` 子命令

```bash
ctl init                    # 一次性初始化 ~/.notify，生成主频道
ctl new-channel <服务名>     # 为某任务建独立频道（想单独静音某个任务时才用）
ctl test <服务名>            # 发一条【测试】消息
ctl status                  # 看所有监控任务状态
ctl stop <服务名>            # 停止某个监控（自动清锁 + 关 tmux 会话）
```

### 频道策略

**默认所有任务共用一个主频道**，手机只需订阅一次。通知标题会自动加 `[服务名]` 前缀，列表里一眼能分清是哪个任务。

只有两种情况需要独立频道：

- 想把某个任务的通知推给别人
- 想单独静音某个任务（在手机上对那个频道静音）

## 十一、设计取舍

写这个 skill 时有意做了几个"反直觉"的决定：

| 决定 | 理由 |
|---|---|
| **禁止监控脚本里写 `curl`** | 优先级映射一旦散落各处，`priority 5` 迟早会被谁再写一遍 |
| **级别只接受语义词，不接受数字** | `notify done` 比 `notify 4` 更能防错——没人会"顺手"改成 5 |
| **判断条件用产物而不是过程文件** | 日志/临时文件是边跑边写的，拿它当完成信号会基于半成品算出错结论 |
| **模板强制 `STABLE` 复检** | 文件"出现了"和"写完了"是两件事 |
| **心跳必须开** | 静默失败是这类脚本最危险的形态 |
| **正文按字符截断** | bash 的 `${var:0:N}` 按字节切，中文会变成 `建�` |
| **测试消息带【测试】前缀** | 用真实完成格式发测试，用户会以为任务真的完成了 |

**这些坑的共同特征：它们都不会报错。** 脚本安静地跑完、安静地给出错误结果、或者安静地什么都没做。

规矩存在的唯一理由，就是把这些"安静的错误"变成"响亮的提醒"。

- bash 4+
- `curl`（发推送）
