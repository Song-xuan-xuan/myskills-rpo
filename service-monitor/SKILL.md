# 任务监控推送

把「等一件事出结果」变成「手机响一声，附一句摘要」。

**适用对象不限于实验**：训练、备份、构建、爬虫、部署、等一个 Agent 的回答、等外部接口变成 `done`、等网页出现某个数字，处理方式完全一样。

---

## 核心模型：任何监控目标都压缩成两条命令

| 配置 | 语义 | 例子 |
|---|---|---|
| `CHECK` | 退出码 **0 = 条件已满足**，非 0 = 继续等 | `test -s answer.txt` |
| `BODY` | 满足后取一行摘要，**stdout 最后一行**就是推送正文 | `tail -1 answer.txt` |

规范本身**不含任何领域知识**。换任务只换这两行。

---

## 频道策略：默认共用主频道

| 情况 | 做法 |
|---|---|
| **默认**（绝大多数任务） | 共用主频道。手机**只需订阅一次**，以后新增任务再也不动手机。通知标题自动带 `[服务名]` 前缀区分 |
| 需要推给别人 / 想单独静音某个任务 / 不想混在同一条通知流里 | 为该任务建独立频道 |

**开工前必须问用户这一次**（见流程第 2 步），不要自己替用户决定。

## 流程：分两个阶段，中间有强制暂停

### Phase 1 — 准备

**① 首次使用先初始化**

先问用户一句：**你手机上已经订阅过某个 ntfy 频道了吗？**

```bash
# 情况 A：用户已有频道（换机器、换 agent、重装系统时最常见）
~/.pi/agent/skills/service-monitor/scripts/ctl init --topic <用户给的频道名>

# 情况 B：全新开始，没有现成频道
~/.pi/agent/skills/service-monitor/scripts/ctl init     # 生成 16 位随机频道名
```

> ⚠️ **有现成频道却跑了不带 `--topic` 的 `ctl init`，是本 skill 最容易致命的一步。**
> 那会生成一个新频道，消息全发到没人订阅的地方，而服务端完全看不出来（HTTP 照样 200）。
> 用户会以为「配好了但收不到」，只能靠翻手机发现没订阅过这个新名字。

两种情况都会生成 `~/.notify/`（config / notify / lib.sh / services / logs / state）。

- 情况 A（沿用）：**不要**再给订阅指引，用户手机上已经订好了，直接进 ④ 跑 `ctl test` 验证
- 情况 B（新建）：输出里带订阅指引，按 ③ 走

**② 问用户：用主频道还是新建独立频道**

> 这次的通知走默认主频道，还是单独开一个频道？
> - 主频道：手机不用再动，通知里靠 `[任务名]` 区分（推荐）
> - 独立频道：需要在手机上单独订阅一次，之后可以单独静音

用独立频道才执行：

```bash
~/.pi/agent/skills/service-monitor/scripts/ctl new-channel <服务名>
```

**③ 如果用了新频道 → 停下，等用户确认订阅**

把 `ctl new-channel` 打印的**频道名原样贴给用户**，并交代：

1. 手机装 ntfy（Google Play / F-Droid / App Store）
2. App 里点 `+` → 粘贴频道名 → 订阅
3. 把 **high 通道**铃声设成短提示音（本工具只发这一档）
4. 把 **max / 紧急通道**关掉或静音（本工具永不使用，该档位在安卓是闹钟式循环响铃）
5. 关闭系统对 ntfy 的电池优化，否则后台长连接会被杀

> ⚠️ **必须在这里停下来等用户回复「订阅好了」再继续。**
> 用户刚看到频道名几秒钟，手机不可能已经订阅完；此时发测试消息一定收不到，
> 而脚本这边看起来一切正常 —— 这是最容易让人误判"配好了"的陷阱。

并说明：ntfy 不支持扫码或点链接自动订阅（功能请求 [#87](https://github.com/binwiederhier/ntfy-android/issues/87) /
[#121](https://github.com/binwiederhier/ntfy-android/issues/121) /
[#1015](https://github.com/binwiederhier/ntfy/issues/1015) 尚未实现），必须手动粘贴，一个字符都不能差。

**④ 写监控脚本**

复制 `templates/monitor.sh` 到 `<项目>/.monitor/<服务名>.sh`，只改 3 个变量：`SVC` / `CHECK` / `BODY`。
服务名用小写连字符（`backup-db`、`agent-codex`、`crawl-blog`）。

> 循环、进程锁、心跳、超时、报错检测、截断、重试都由 `lib.sh` 提供 —— **不要重写这些**。

### Phase 2 — 验证与启动

**⑤ 发测试消息，等用户确认收到**

```bash
bash <项目>/.monitor/<服务名>.sh --test      # 或 ctl test <服务名>
```

- **新频道**：必须跑，且必须等用户回复「收到了」才能启动
- **主频道**：已经验证过，可以不跑；但任务关键时仍建议跑一次

**⑥ 后台启动并交付启停命令**

```bash
mkdir -p ~/.notify/logs
tmux new-session -d -s <服务名> \
  'bash <项目>/.monitor/<服务名>.sh >> ~/.notify/logs/<服务名>.log 2>&1'
```

> 用重定向而不是 `| tee`：没开 `pipefail` 时管道的退出码是 `tee` 的，
> 脚本崩了也被吞掉，看不出来。

交付时必须给用户：

| 项 | 内容 |
|---|---|
| 启动 | 上面那条 tmux 命令 |
| 看日志 | `tail -f ~/.notify/logs/<服务名>.log` |
| 看全部任务 | `ctl status` |
| 停止 | `ctl stop <服务名>` |
| 重跑 | 先 `ctl stop`，再重新执行启动命令 |

## 规矩：agent 必须自己想清楚的 13 条

凡是能由 `lib.sh` 强制的，都不在这里 —— 这里只留需要判断力的事。

### A 组 · 判断信号（最容易出错的地方）

| # | 规矩 | 不遵守会怎样 |
|---|---|---|
| A1 | **完成信号必须用产物，不能用过程文件**。若只能盯过程文件，必须设 `STABLE`（条数达标 + 文件静止 N 秒） | 边写边刷的文件一出现就被判完成，基于半成品算出错误结论推给用户 |
| A1b | **判断「文件存在」用 `test -f`，不要用 `test -s`** | `test -s` 要求文件**非空**；而 `touch` 造的标记文件是 0 字节，于是条件永远不成立 —— 实测踩过：任务明明成功了，却推了一条「异常终止」 |
| A2 | **必须幂等**：用处理产物当哨兵（如 `judged_*.json`），已通知过就跳过 | 重跑一次又推一次，用户以为任务又完成了一遍 |
| A3 | **判断逻辑只读**，不产生副作用（删除/移动文件另放一步） | 中断后重跑会破坏数据 |
| A4 | **长任务要配存活探针**：`WATCH_PID` 或 `WATCH_PATTERN` | 进程 OOM 挂掉后产物永不出现，只能干等到超时，可能白等一整天 |
| A5 | 脚本头部留注释：监控什么 / 完成信号是什么 / 为什么这个信号可靠 | 三天后自己不敢改也不敢删 |

### C 组 · 消息内容

| # | 规矩 | 不遵守会怎样 |
|---|---|---|
| C1 | **摘要只取一行**，靠 `BODY` 的最后一行约定，别塞长文 | 手机通知栏放不下；`BODY_MAX` 会截断，完整内容只在日志里 |
| C2 | **测试消息必须带 `【测试】` 前缀，且一次只发一条** | 用户会把演练当成真实完成通知 |
| C3 | **正文不含密钥、内部地址、用户隐私**，绝对路径尽量缩短 | ntfy.sh 是公开频道，消息还会经过 FCM 推送管道 |
| C4 | **完成通知必须自解释**：只看通知也能知道是哪个任务、结果多少 | 一天收到好几条时只剩编号，分不清 |

### D 组 · 交付给用户

| # | 规矩 | 不遵守会怎样 |
|---|---|---|
| D1 | **频道名 + 订阅指引**原样贴出 | 用户拿不到频道名，整条链路白做 |
| D2 | 新频道**必须先测试并等用户确认收到**，再启动正式监控 | 频道名打错是唯一会让全链路失效的原因，而**服务端完全看不出来**（ntfy 对任意 topic 开放写入，`curl` 照样 200） |
| D3 | 后台启动 + 给出日志路径 | SSH 一断，前台脚本跟着死 |
| D4 | 说明**怎么停、怎么重跑** | 只能启动不能停，出问题只能杀进程 |

## 已由工具保证，agent 不用操心

| 机制 | 谁保证 | 解决什么 |
|---|---|---|
| 唯一推送出口（禁止 curl） | `~/.notify/notify` | 优先级映射散落各处 |
| 级别只接受 `done/start/warn/info` | CLI 参数校验 | 根治 priority 5 |
| 进程锁 | `lib.sh` | 误开两次导致双倍通知、状态互踩 |
| 心跳日志 | `lib.sh` | 「还在等」和「脚本死了」外观相同 |
| 超时退出 + `warn` | `lib.sh` | 任务卡死无人知晓 |
| CHECK 语法预检 | `lib.sh` | 拼错的命令安静空转到超时 |
| 退出码 126/127 致命判定 | `lib.sh` | 命令不存在被当成「还没好」，永远等下去 |
| 正文按**字符**截断 | `lib.sh` | bash `${var:0:N}` 按字节切，中文变 `建�` 乱码 |
| 空正文兜底 | `notify` | 空 body 被接口拒发 |
| 发送重试 3 次（1s/3s/9s） | `notify` | 网络抖一下就把完成通知弄丢 |
| 日志轮转（5MB × 3 份） | `lib.sh` | 跑几十个任务后日志撑爆磁盘 |
| 推送审计 `sent.jsonl` | `notify` | 事后无法追溯发过什么 |

## 四类任务范例

| 类型 | 典型场景 | `CHECK` | `BODY` |
|---|---|---|---|
| **完成型** | 训练 / 备份 / 构建 / 批处理 | `test -f out/done.json`（配 `STABLE=60`） | `du -h backup.sql.gz \| cut -f1` |
| **响应型** | 等一个 Agent 的回答 / 等外部 API 终态 | `grep -q '"status": *"completed"' resp.json` | `tail -1 answer.txt` |
| **内容型** | 网页或日志出现关键字 | `curl -sf https://x/status \| grep -q "已上线"` | `grep -o "版本 v[0-9.]*" deploy.log \| tail -1` |
| **阈值型** | 进度到达 100% | `[ "$(cat progress.txt)" -ge 100 ]` | `cat progress.txt` |

**这四类只是起点，不是封闭集合。** 任何能写成「一条返回 0 / 非 0 的命令」的条件都能接入。

### 等一个 Agent 的回答（响应型详解）

```bash
SVC='agent-codex'
CHECK='test -s /tmp/agent_codex_answer.txt'        # 答案落盘且非空
BODY='tail -1 /tmp/agent_codex_answer.txt'         # 最后一句就是摘要
WATCH_PATTERN='codex'                              # Agent 进程挂了立刻告警，别傻等
TIMEOUT=3600
```

## 禁止事项

- ❌ 在监控脚本里写 `curl` 发 ntfy（必须走 `~/.notify/notify`）
- ❌ 使用 priority 5 / max（安卓闹钟式循环响铃）
- ❌ 用真实完成格式发测试消息
- ❌ 正文包含密钥、token、内部系统地址、真实用户数据
- ❌ 用过程文件当完成信号却不设 `STABLE`
- ❌ 用户已有现成频道却用 `ctl init` 生成了新频道（应使用 `ctl init --topic`）
- ❌ 用户还没确认订阅就发测试消息并启动监控
- ❌ 在 `tmux` 命令里用 `| tee`（管道会吞掉退出码）

## 交付前自查清单

- [ ] 已问过用户：手机上是否已有订阅过的频道（有则用 `--topic` 沿用）
- [ ] 已问过用户：主频道还是独立频道
- [ ] 若用独立频道：频道名已原样贴出，且**用户已确认订阅完成**
- [ ] 已跑 `--test`，且**用户确认手机收到**
- [ ] `CHECK` 已验证：条件未满足时确实返回非 0（没有写成恒真的 `true`）
- [ ] `CHECK` 用的是**产物**而非**过程文件**；必要时设了 `STABLE`
- [ ] 长任务配了存活探针（`WATCH_PID` / `WATCH_PATTERN`）
- [ ] 已用 tmux 后台启动，并给了日志路径
- [ ] 已告知怎么停、怎么重跑
- [ ] 脚本里没有 `curl`，没有 priority 5
- [ ] 推送内容不含敏感信息

## 已知坑（规矩背后的真实事故）

| 事故 | 后果 | 对应规矩 |
|---|---|---|
| 把「文件出现」当作「完成」 | 基于半成品数据算出错误结论并推送，用户据此做错判断 | A1 |
| `curl` 没加 `-f`，HTTP 4xx 仍返回 0 | 日志写「已推送成功」，实际没人收到，白等几小时 | 已内置 |
| 测试消息用真实完成格式 | 用户以为任务真的完成了 | C2 |
| 循环里没有心跳 | 「还在等」和「已挂掉」外观完全一样 | 已内置 |
| 用了 priority 5 | 手机铃声一直响到手动划掉 | 已内置 |
| 重跑同一任务又推一遍 | 用户以为任务又完成了一次 | A2 |
| `${var:0:N}` 按字节截断中文 | 通知里出现 `建�` 乱码 | 已内置 |
| **`test -s` 判 0 字节的标记文件** | 任务成功了，却推「异常终止」，还白等一个 STABLE 周期 | A1b |

**这七条的共同特征：它们都不会报错。** 脚本安静地跑完、安静地给出错误结果、或者安静地什么都没做。
规矩存在的唯一理由，就是把这些"安静的错误"变成"响亮的提醒"。
